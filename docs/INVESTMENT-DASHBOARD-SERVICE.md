# 투자비 대시보드 서비스 정리

## 1. 서비스 목적

사내 투자사업의 일정과 투자비를 한 화면에서 조회하고, 실무담당자와 관리자가 사업정보·투자비 자료를 관리하는 웹앱이다.

- 임원·직책자: 전체 사업과 투자비를 조회
- 실무담당자: 일정·Rolling Plan 입력, 투자비 엑셀 업로드, 확정
- 관리자: 사업정보·권한·투자비를 관리하고 확정된 사업도 수정

현재는 시연 및 안정화 단계이며, 최종적으로 회사 시스템과 투자오더·투자비 데이터를 연동한다.

## 3. 화면 구성

### 로그인

사번과 비밀번호로 로그인한다. 현재 Supabase Auth가 적용되어 있어 Supabase에 등록된 계정만 로그인할 수 있다.

### 대시보드

- 좌측: 양극재·음극재 소재별 사업현황 도넛 차트
- 도넛 hover: 좌측 영역 안에 해당 소재의 사업목록 표시
- 우측: 사업별 투자비 바 차트
  - 승인투자비를 사업별 100% 기준으로 표시
  - 누적투자비는 승인투자비 대비 비율로 표시
  - 현재 색상 기준: 누적투자비 밝은색, 승인투자비 어두운색
- 하단: 사업목록
  - 사업명
  - 계획·실적 일정
  - 투자비 현황(승인·누적·잔여·누적률)
  - 긴 사업명은 셀 안에서 자동 줄바꿈
  - 실적 사유가 있는 날짜는 굵은 글씨와 밑줄로 표시되며 hover 시 날짜 아래에 사유 표시

### 사업 상세

- 사업 기본정보
- 승인투자비·누적투자비·집행률
- 주요 일정(사업승인, 토건착공, 기전착공, 준공(시운전완료), SOP)
- 분기별 Rolling Plan 비교
- 당해년도 분기 선택 시 월별 계획·실적 상세
- 월별 차이 사유

### 사업 관리

실무담당자와 관리자가 사용할 수 있다.

- 사업 추가
- 사업명·소재지·소재·사업상태 수정
- 승인투자비 입력·수정
- 계획·실적 일정 입력
- 실적 지연·선행 사유 입력
- 연도별 Rolling Plan 계획금액과 사유 입력
- 관리자만 사업 활성화·비활성화와 사용자 권한 관리 가능

### 투자비 가져오기

- 여러 개의 `.xlsx` 또는 `.xls` 파일을 반복 업로드
- 파일 업로드 후 모든 투자오더를 사업명과 연결
- 이미 연결된 사업명은 자동 선택
- 하나의 사업에 여러 투자오더 연결 가능
- 여러 월·여러 투자오더의 투자비를 하나의 사업으로 합산
- 확정된 사업은 실무담당자 수정 잠금
- 관리자는 확정 이후에도 수정 가능

## 4. 엑셀 처리 규칙

샘플 보고서에서 다음 항목을 사용한다.

| 위치 | 의미 |
|---|---|
| B열 | 오더/그룹 및 투자오더번호 식별 |
| B5 | 리포팅 기간(월·연도) |
| C14 | 월별 실적투자비 |
| C15:C108 | C14와 비교하는 검증 합계 범위 |
| B109의 `* H,S` | 사용 범위 종료 표시. 실제 사용 범위는 108행까지 |

검증 순서:

1. 파일명과 오더번호 확인
2. 보고 기간 확인
3. C14 월별 실적투자비 추출
4. C15:C108 합계와 C14 일치 여부 확인
5. 검증 통과 행을 사업별 투자오더에 연결
6. 월별 실적투자비를 합산해 누적투자비 계산

환입·조정 등으로 음수가 발생하는 경우도 원본 값 그대로 반영한다.

## 5. 투자비 계산

- 월별 실적투자비: 각 월 파일의 C14 값
- 사업별 월별 투자비: 동일 사업에 연결된 투자오더들의 해당 월 합계
- 누적투자비: 월별 실적투자비의 누적 합계
- 잔여투자비: 승인투자비 - 누적투자비
- 누적률: 누적투자비 ÷ 승인투자비 × 100

## 6. 권한 정책

| 역할 | 대시보드 | 사업 관리 | 투자비 가져오기 | 수정 범위 |
|---|---:|---:|---:|---|
| viewer | 가능 | 불가 | 불가 | 조회만 가능 |
| staff | 가능 | 가능 | 가능 | 확정 전 자료 수정, 확정 후 잠금 |
| admin | 가능 | 가능 | 가능 | 모든 자료와 확정 사업 수정 가능 |

현재 권한은 Supabase `public.user_roles` 테이블에서 관리한다.

## 7. Supabase 구성

현재 사용 중인 Supabase 프로젝트에는 다음 테이블이 있다.

- `user_roles`: 사용자별 viewer·staff·admin 역할
- `projects`: 사업정보와 일정 JSON
- `investment_transactions`: 파일별·행별 투자비 원천 데이터
- `order_mappings`: 투자오더와 사업 연결
- `project_finalizations`: 사업별 확정 상태

모든 테이블은 RLS가 활성화되어 있으며, 로그인한 사용자만 조회할 수 있다. 사업·투자비 변경은 staff 또는 admin 역할만 가능하다.

## 8. 계정 등록 절차

1. Supabase Dashboard의 **Authentication → Users → Add user**에서 계정 생성
2. 앱 로그인 시 사번은 계정 이메일의 앞부분을 사용
   - 예: `123456@investment.local` → 앱 사번 `123456`
3. 기본 역할은 `viewer`
4. 실무담당자·관리자는 `public.user_roles`에서 역할 지정

관리자 역할 지정 예시:

```sql
insert into public.user_roles (user_id, employee_id, role)
select id, '123456', 'admin'
from auth.users
where email = '123456@investment.local'
on conflict (user_id)
do update set role = 'admin';
```

## AI Agent 운영

### 사용 방법

- 로그인한 사용자는 상단 메뉴의 **AI Agent** 또는 `/agent`에서 투자비 이상 징후, 계획 대비 실적 차이, 누락된 일정·오더 매핑, 업로드 워크북, 안전 규정을 분석할 수 있다.
- Agent 화면과 플로팅 안전 챗봇은 모두 `/api/agent` 게이트웨이만 호출한다. 브라우저는 프로젝트·투자비 저장소나 Supabase 테이블을 직접 호출하지 않는다.
- 안전 답변은 승인된 안전 문서에서 찾은 근거만 사용하며, 근거가 있으면 제목·절·링크를 함께 표시한다. 승인된 근거가 없으면 해당 사실을 명시한다.
- 분석 제공자를 사용할 수 없을 때는 Agent가 임시 장애 안내만 반환하며, 초안·승인·저장 경로를 노출하지 않는다.

### Agent 환경 변수

클라이언트와 서버리스 함수에는 동일한 Supabase 프로젝트 정보를 각각의 이름으로 설정한다. 실제 키는 저장소나 문서에 커밋하지 않는다.

| 위치 | 변수 | 용도 |
|---|---|---|
| Vite 클라이언트 | `VITE_SUPABASE_URL` | Supabase 프로젝트 URL |
| Vite 클라이언트 | `VITE_SUPABASE_PUBLISHABLE_KEY` | 로그인 세션을 위한 publishable key |
| `/api/agent` 서버리스 함수 | `SUPABASE_URL` | Bearer 토큰 검증과 역할 조회용 Supabase URL |
| `/api/agent` 서버리스 함수 | `SUPABASE_PUBLISHABLE_KEY` | 서버 측 인증 클라이언트 key |

현재 Agent 게이트웨이는 제공자 중립형 인터페이스를 사용한다. 특정 LLM 제공자 키나 모델 이름을 설정해도, 서버 측 adapter를 별도로 구현·등록하기 전에는 사용되지 않는다. 이 상태에서는 안전한 분석 불가 응답으로 대체된다.

### 권한 및 승인 규칙

| 역할 | 분석 | 초안 승인·저장 |
|---|---|---|
| `viewer` | 가능 | 불가 |
| `staff` | 가능 | 서버가 보관·검증한 초안에 한해 가능 |
| `admin` | 가능 | 서버가 보관·검증한 초안에 한해 가능 |

- AI는 Supabase나 로컬 저장소에 직접 쓰지 않는다. 변경은 타입이 정해진 초안 생성, 사용자 명시 승인, 권한·검증 재확인, 기존 저장소 mutation, 감사 로그 기록 순서로만 처리한다.
- 워크북 가져오기 초안은 월 실적 `C14`와 상세 합계 `C15:C108`가 일치해야 승인할 수 있다. 음수 조정은 유효한 값으로 보존한다.
- 현재 배포 경로에는 서버 소유의 pending-draft 저장소가 연결되어 있지 않다. 따라서 명시적 변경 요청은 `PENDING_DRAFT_STORAGE_UNAVAILABLE` 상태로 표시되며, `staff`와 `admin`에게도 승인·취소 버튼을 숨긴다. 이 경우 화면은 저장 성공을 표시하지 않는다.
- 승인된 변경이 실제로 저장되는 배포 구성에서는 모든 persisted Agent action에 감사 로그를 남겨야 한다.

- 업로드·검증·확정 감사 로그
- 실무담당자 지정 화면의 Supabase 서버 저장
- 운영 환경에서의 세부 RLS 및 승인 프로세스 강화
